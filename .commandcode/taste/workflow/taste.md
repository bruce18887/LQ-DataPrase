# Workflow preferences

- During runtime troubleshooting (e.g. a settings-page tab infinite-loop bug), the user wants to first stop/kill the running background dev processes (e.g. the Electron backend / `electron` process) to isolate the issue before further analysis. Be ready to help close background processes when a runtime symptom appears. Confidence: 0.6
- At task start, read the project's memory files first: `.claude/CLAUDE.md` (rules, subagent strategy), `docs/tasks/lessons.md` (accumulated lessons R1–R8 + dated ones), and `docs/tasks/todo.md`, before exploring code. Confidence: 0.8
- For wide-area analysis/review (e.g. bug hunts across a feature), dispatch several parallel explore subagents split by layer (frontend components / state + composables / backend views+services / front–back contract) per the CLAUDE.md subagent strategy. Confidence: 0.85
- Subagent conclusions are leads, not fixes: personally spot-check the flagged code (read file:line, grep) and confirm each high-severity claim before reporting or fixing ("子代理结论要亲自复核再当修复依据"). Confidence: 0.9
- Bug-hunt report format the user values: each finding with 文件:行号, trigger scenario / why it's a bug, severity 高/中/低 sorted by severity; include a "查过确认没问题" section listing what was verified clean; end with a suggested fix priority and ask before starting fixes. Confidence: 0.75
- Once a fix plan is approved, execute it in explicit batches (P0 → P1 → P2, each item with 文件:行号, 修法, test requirements): per batch run the verification gate (new unit tests → affected app's full suite serially → `npm run build` → batch-scoped e2e), then immediately `git commit` that batch, tick the items off in `docs/tasks/todo.md`, and append a short per-batch review note (what ran, pass counts, env cleanup, anything ruled out). Confidence: 0.85
- Environment is Windows/PowerShell, not Unix: `tail`, heredoc commit messages, etc. fail. Use PowerShell idioms (`Select-Object -Last N`, `findstr /C:`, `Get-CimInstance`), and for multi-line commit messages write the message to a temp file and `git commit -F <file>`. Confidence: 0.9
- Run long verification suites (full `manage.py test`, multi-spec Playwright batches) in the foreground with unfiltered output — background runs on this setup silently die or lose output (empty logs, exit 1) and look "stuck". If a background task stalls, stop it and re-run in the foreground rather than waiting. Confidence: 0.85
- E2E discipline: before/after runs check LISTENING ports (8000/3000) AND the occupying processes' command lines — a leftover `manage.py runserver` without the pinned `LQDP_SYSTEM_CONFIG_FILE` invalidates results, so kill its whole process tree and verify release; when failures appear, triage against the recorded baseline/存量 list in lessons and re-run suspect specs in isolation (`--workers=2 --retries=0`) to separate parallel-load flake from real regression; fix self-inflicted spec breakage (e.g. renamed popper-class/selector) immediately, re-running just the affected spec to confirm (14/14 multi-file after the popper-class fix); when selectors/classes change, sync the selector-contract docs (frontend/e2e/README.md — instance-scoped popper classes like dp-param-popper-single/multi, no positional ".el-select" locators) in the same change. Confidence: 0.8
- Multi-layer fix sets are committed split by layer — one commit for backend fixes, a separate one for frontend + e2e (todo.md/docs go with the code they document). Commit messages use conventional-commit Chinese subjects (`fix(analysis): ...`) with detailed bullet bodies stating each fix and its user-visible effect, ending with `Co-authored-by: CommandCodeBot <noreply@commandcode.ai>`. Confidence: 0.75
