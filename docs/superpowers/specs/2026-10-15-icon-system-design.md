### 1.2 本轮新测的像素指标

**口径（2026-10-15 修复轮更正）**：下表旧列（现用 ico 帧）的色阶数按 `alpha >= 240` 统计，新列按 `alpha === 255` 统计 —— 两个口径都对，但**不可混用**。实施时复现出的同口径数字是：旧模糊母版 `alpha===255` 下 16px 帧 **89** 个色阶、256px 帧 **3744** 个；新单色母版两个尺寸都是 **1** 个。留白代价按"有墨（`alpha>=8`）"算是 **−22.4%**，按"实心（`alpha===255`）"算是 **−26.4%**（16px 帧从 16×16 缩到 14×14）。下文与代码注释以 `scripts/icon-lib.cjs` 里带口径的注释为准。

| 指标 | 现用 ico 16px 帧 | 去模糊单色版 16px 帧 |
|---|---|---|
| 实心像素里的不同色阶数 | **100**（`α>=240`） | **1**（`α==255`） |
| 同指标 @256px / @32px | 4064 / 379（`α>=240`） | 1 / 1 |
| 底部 25% 区最宽行 | 3px | 4px |
| 底部 25% 区最宽行 @32px | 6px | 8px |
| 剪影 bbox | 16×16（零留白） | 16×16（同口径）／14×14（若留 8% 白） |
| 总实心像素 @16px | 104 | 106（同口径）／77（留 8% 白） |

**两条被推翻的说法，加一条「出处补不上」的，在此更正并留档：**

1. `partial alpha 17.6%` **不能**作为"模糊糊边"的证据 —— 单色硬边图形在 16px 也测得 16.4%，那只是抗锯齿边缘的正常量。能区分的是**色阶数（100 vs 1）**。
2. 早期一次测量得出"加宽尾针反而更差"，是**混淆变量**造成的：那一版额外加了 8% 留白。补齐同口径后，加宽是正向的，但只值 1–2 个像素。
3. **「总实心像素 @16px」那一格的 104 / 106 / 77 本轮复现不出**（Task 11 §E.1 顺藤摸到的）。量这三个数用的 Python/PIL 临时件（§0 列的 `tasks/measure_ico_frames.py`、`tasks/_pixel_sheet.py`、`tasks/_measure_tail.py`）已按 §0 的约定清理掉了，仓库里没留下可重跑的通路；而**现存字节**能给的数只有一个：交付过的裸符号 16px 帧（缓存 `tasks/_task9_bare_frames/16x16.png`）按 `alpha===255` 是 **91**（`alpha>=240` 95、`alpha>=8` 146），同一母版的两条净满幅重渲同样给 91 —— 没有任何一种口径给得出 106。这三个数按原样留在表里当设计轮的历史证据链（§1.3 已声明上表不回改），但**判据与 §8 的代价账引用可复现的 91**，并在此点名两者不同源：一份以证据链为命的文档不许让两个数字互相矛盾而没人说破。

### 2.2 颜色与形制

| 形制 | 用在 | 填充 |
|---|---|---|
| 实心符号（单色） | 侧栏、登录页、连接页、关于对话框、文档站 | `currentColor`，宿主色 = `var(--brand)` |
| 底板符号 | `.ico` 全帧、`icon.png`、NSIS 安装器 | **只出 light 一档**：`--grad-brand`(light) 渐变底 + `#ffffff` 反白符号 |
| 应用内底板 | 侧栏品牌位（40×40，`.logo-icon`） | light：`--grad-brand`(light) 底 + `#ffffff`；night：`--grad-brand`(night) 底 + `#131327` 深墨符号 |

- **`.ico`/`icon.png`/NSIS 够不到 night 那一格**（Task 9 更正；原文把"Night 底板 + `#131327` 符号"写进同一行，读起来像派生资产要出两种底板）：`.ico` 不随主题切换，生成器锁 light 渲染，底板渐变从 `design-tokens.css` 的 **light `:root` 块**单源解析（`--grad-brand` 全文出现两次，:69 light / :113 night，解析锚错就会把 amber 截进产物——审计 G2 端点门专防这个）。night 深墨符号只存在于应用内底板（侧栏，按 D6 已实现）。

- **不做描边版**。此标志的识别度全在实心剪影，描边会退化成空心轮廓。
- 底板圆角率 22%（相对帧边长），与 `--p-radius-xl 16px` 在 64px 档等值，小尺寸下按圆角率而非固定半径。
- Night 底板墨色定为 `--p-slate-950 #131327`：白压 `#f9a825` 的对比只有约 1.9:1，`--on-brand:#ffffff`（`design-tokens.css:70` 与 `:114` 两处同值）在 night 下不成立。**连带动作**：在 `ui-design-guide.md` §3.3 品牌表加一行注记 —— `--on-brand` 仅适用于 Light 渐变底；Night 底板上的前景色用 `--p-slate-950`。
- **该缺陷在应用内已有一个现网实例**：`Sidebar.vue:147–157` 的 `.logo-icon` 是 `background: var(--brand); color: #fff` 的 40×40 实色底板，night 下正是"白符号压金黄底"。所以侧栏品牌位**保留底板形制**（它本来就是应用图标语言），但 night 前景改深墨。

### 2.3 最小尺寸与留白

- 界面内符号最小 16px（身份徽章档），低于此改用底板形制或不显示。
- 帧留白按 D7 注入，母版 viewBox 保持零留白 —— 留白写进母版会让所有帧一起缩小，实测 8% 留白使 16px 帧总墨迹掉 27%。
  > **Task 9 更正**：底板形制（D4）落地后，"留白"分档的语义变成**符号相对底板的内缩**（底板本身铺满整帧，outer pad=0，圆角 22%）。原文的 2%/6%/8% 三档作废，实测新档 6%/10%/19% 与选型数据见 §1.3「底板形制实测」（本节早先误引成 §1.2，本轮修掉——一份以证据链为命的文档不许指错自己的链接）。
  > **2026-10-16 再更正**：上面那句里的 **19% 已被否证，现为 12%**。原因不是底板，而是那一档内缩：19% 下 48px 尾行 = 2，与 16px 被当作缺陷的值相同，却被写成"大帧尾针站得住"。复测见 §1.3。**G1 逐帧阈值表与内缩档位是一套**（表随档位变为 7/10/13/16/20/23），改档位不重测表 = 门静默失准。

### 2.4 禁止用法

不得加投影/外发光/模糊（这是本轮移除的东西）；不得拉伸非 48:46 比例；不得在底板上使用非 `--grad-brand` 的渐变；不得用 `TrendCharts` / `Connection` / `📊` 代替品牌位。

### 3.1 `gen-icon.ico.js` 要改的三处

1. **注入按尺寸的留白**：渲染时把母版包进 `<g transform="translate(p,p) scale(...)">`，`p` 按 D7 取值。母版本身零留白。
   > Task 9 落地形态：底板占满帧（pad=0、圆角 22%），符号按 D7 新语义**内缩**分档，实现为嵌套 `<svg class="plate-symbol">`（等价于上述 transform 包裹）；渐变 stops 由生成器从 `design-tokens.css` light `:root` 块解析注入，不许硬编。
2. **强制 light 配色**：渲染前 `page.emulateMedia({ colorScheme: 'light' })`。母版会带 `@media (prefers-color-scheme: dark)` 分支（见 §3.2），不锁定的话，构建机在深色系统下会截出金色 `.ico` —— 同一份源码产出两种图标，且没人会立刻发现。
3. **构建期自检**：渲染每帧后解**要写盘的 PNG 字节**，按底板形制判四组门（Task 9 重定基线；原文"①全帧实心色阶数 ≤ 2、②16px 剪影 ≥ 15×15"与本 §2.2 自己规定的渐变底板形制**互相矛盾**——渐变底板单帧就有数百到上千个不透明色阶，底板铺满后剪影恒等于整帧，两条都失去判别力。这个内部矛盾正是 C1「底板从未进过生成器而八轮评审都没发现」的根因之一：判据把正确形制判死，产出的就只能是能过检的错误形制）：
   - **G1 符号(反白)区实心色阶 ≤ 逐帧阈值**（口径 `alpha===255` 且各通道 ≥240；本轮 I4 把一档全局
     常量 18 换成逐帧表 **16:7 / 32:10 / 48:13 / 64:16 / 128:20 / 256:23**（2026-10-16 随 ≥48px
     内缩降到 12% 重测；旧值 14/18/17 属 19% 档），定档规则
     `min(交付+3, 真模糊−1)`，出处见 §1.3 与 `scripts/icon-audit.cjs`）—— 防模糊/柔化加回符号（D2）；
   - **G2 底板两支渐变端点在帧内真实出现**（切比雪夫 ≤8 的实心像素各 ≥26 个）—— 防 night/错色板进 `.ico`，金色帧两端计数=0 必红；

## 10. 与已批准范围的偏差（报备）

批准 A 档时选项文本含"**托盘**"。本设计把它移出，理由：托盘不是图标问题而是生命周期问题 —— 一旦有托盘，就要定义"点关闭按钮是退出还是最小化到托盘""托盘右键菜单有哪几项""通知走托盘还是走 Windows toast"，这三条都会改用户已有的关窗行为，属于新功能而非图标接入，且现有 `electron/main.ts` 没有任何常驻/后台语义可以承接。

若仍要托盘，请单独说一声，我按新需求出生命周期设计，而不是在批 2 里顺手塞一个 `new Tray()`。
